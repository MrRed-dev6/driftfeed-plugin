# plugin-tiktok

Настоящий источник данных: лента, поиск по хештегам, видео по id, профиль,
комментарии. Реализует контракт `Provider` из `provider-api`, поэтому для
клиента он неотличим от тестового провайдера.

## Как устроено

```
TikTokProviderFactory   ← entryClass для sources.json
  └── TikTokProvider    ← Provider, объявляет capabilities по факту
        └── TikTokApi   ← решает, куда идти за каждым разделом
              ├── TikTokHtml    ← достаёт JSON из <script> внутри страницы
              ├── TikTokParser  ← разбор полей, терпимый к переименованиям
              └── TikTokGateway ← публичный шлюз: лента и комментарии
```

## Откуда данные

Две дороги, и это осознанный компромисс: часть данных у TikTok открыта
напрямую, часть — только через посредника.

### 1. `/embed` сайта TikTok — напрямую

Страницы-«встройки» отдают данные обычным HTML: подпись не нужна, cookie не нужны.

| Запрос | Что внутри |
|---|---|
| `GET /embed/@<ник>` | `userInfo` (ник, имя, аватар) и `videoList` — 10 последних видео |
| `GET /embed/<id видео>` | `videoData.itemInfos` (описание, ссылка на поток, обложки, лайки, комментарии) и `authorInfos` |
| `GET /embed/tag/<тег>` | `videoList` — 10 видео этого хештега |

Данные лежат в `<script id="__FRONTITY_CONNECT_STATE__">` как JSON, в
`source.data[<маршрут>]`. Имя ключа — сам маршрут, поэтому код берёт первый
объект, кроме служебного `strategy`, а не ищет фиксированное имя.

### 2. Шлюз `tikwm.com` — только лента и комментарии

| Запрос | Что внутри |
|---|---|
| `GET /api/feed/list?region=US&count=20` | случайная порция ленты: `video_id`, `play`, обложки, лайки, комментарии, `author` |
| `GET /api/comment/list?url=<id>&count=20&cursor=<смещение>` | `data.comments[]`, `data.total`, `data.hasMore` |

Ни ленты, ни комментариев нет в `/embed`, а веб-API их не отдаёт (см. ниже),
поэтому сюда уходят только эти два раздела. Профиль, видео и поиск идут
напрямую в TikTok — на шлюз не уходят даже id профилей.

**Что это значит для пользователя:** id видео и запрос ленты видит сторонний
сервер. Это записано и в `TikTokGateway`, чтобы через полгода никто не
удивился, откуда в коде чужой домен.

### Почему не через `/api/*`

Пробовал, не работает — и это не вопрос подписи.

- Без подписи: `{"status_code": 0}` или 0 байт.
- С настоящими серверными cookie (`ttwid`, `tt_csrf_token`, `tt_chain_token`) — 0 байт.
- С `X-Bogus`, посчитанным известным алгоритмом, — 0 байт.
- С `X-Gnarly` на чистом JS (`abogus`, без браузера) и настоящими `ttwid`,
  `msToken`, `tt_webid_v2`, `s_v_web_id` — подпись **принимается**: вместо нуля
  приходит структура. Но данных в ней нет: `user/detail` →
  `{"userInfo":{"user":{},"stats":{}}}`, `recommend` → `{"status_code": 0}`,
  `comment/list` и `search` → 0 байт. То есть TikTok решает, что запрос валиден,
  и всё равно не отдаёт данные — значит дело не в подписи, а в том, кому он
  их выдаёт.
- С `webmssdk.js` — не выйдет: 243 КБ обфусцированного JSVMP, который падает
  даже в node без полного браузерного окружения, а в QuickJS тем более.
  Мобильное API приложения требует актуальную версию клиента и `X-Gorgon` —
  отдельная реверс-инженерия.

`/embed` и шлюз — единственные пути, которые отдают настоящие данные.

## Чего нет и почему

- **Поиска по словам.** Поиск идёт по хештегам: запрос превращается в тег
  («cat videos» → `#catvideos`). Если хештег из всей фразы не существует,
  проверяется самое длинное слово фразы — по нему видео находятся почти всегда.
  Полнотекстового поиска (по описаниям, музыке, авторам) без подписи нет:
  официальный `/api/search/general/full/` отдаёт пустое тело, а у шлюза поиск
  закрыт Cloudflare.
- **Фотопостов.** Они приходят без ссылки на поток (`play` пустой), поэтому
  в ленту и поиск не попадают: проигрывать там нечего. При прямом запросе
  такого поста `getVideo` отвечает понятной ошибкой, а не пустым плеером.
- **Настоящей постраничности в поиске.** `/embed` отдаёт ровно одну страницу,
  `?page=2` возвращает те же 10 видео. Поиск отдаёт одну страницу,
  `hasMore = false`.
- **Курсора ленты у шлюза.** Шлюз отдаёт случайную порцию и не принимает
  `cursor`, поэтому курсор плагина — просто номер страницы: прокрутка не
  упирается в конец, но повторные видео возможны. Дедупликация — на клиенте.
- **Ответов на комментарии.** Шлюз отдаёт только верхний уровень; счётчик
  ответов (`reply_total`) есть, а сами ответы — нет.

## Настроек и состояния нет

Регион, язык, user-agent, адрес шлюза и размеры страниц — константы в
`TikTokConfig`. Клиент — чужая сторона, и новый метод конфигурации пришлось бы
протаскивать через общий контракт. Меняется выпуском новой версии плагина.

Состояния тоже нет: ни `msToken`, ни cookie, ни `getStorage`. Раньше плагин
поднимал сессию и подписывал запросы — вместе с переходом на `/embed` это
стало ненужным и удалено, а не оставлено «на всякий случай».

## Что нужно от клиента

1. `ProviderContext` с `httpGet` и `log` — реализация на стороне клиента
   (`ClientProviderContext`). `evalJs`, `getStorage`, `setStorage` плагин
   не вызывает.
2. `DexClassLoader` с `parent = classLoader приложения`, иначе классы
   `dev.client.provider.*` не найдутся.
3. `capabilities.comments = true` — клиент может показывать комментарии.

## Сборка

```bash
bash tools/build-plugin.sh keygen   # один раз, создаёт Ed25519-ключ
bash tools/build-plugin.sh          # dist/provider-tiktok.jar + sources.json
```

Скрипт прогоняет классы через `d8`, потому что `DexClassLoader` грузит только
`classes.dex`, а не `.class`.

## Тесты

```bash
gradle :plugin-tiktok:test
```

Проверяют извлечение JSON из HTML (в том числе порядок атрибутов в теге
и страницу-заглушку WAF) и разбор полей: лента и комментарии шлюза, видео,
профиль, хештег из поискового запроса, ник из ссылки.

## Сборка на телефоне не работает

JVM под proot не запускается: Android запрещает исполняемые страницы памяти,
`Failed to mark memory page as executable`. Собирать — только на компьютере
или в GitHub Actions.
