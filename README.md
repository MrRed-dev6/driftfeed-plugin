# tiktok-plugin

Репозиторий плагина источника данных для клиента TikTok. Клиент живёт отдельно
и пишется не здесь: этот репозиторий выпускает `.jar`, который клиент скачивает
по `sources.json` и грузит через `DexClassLoader`.

## Что внутри

```
provider-api/   вендорная копия контракта клиента (только интерфейсы)
plugin-tiktok/  сам плагин: лента с рекомендациями, поиск, видео, профиль, комментарии
tools/          сборка релизного файла: jar → d8 → jar с classes.dex → подпись
.github/        сборка и релиз на GitHub Actions
```

**`provider-api` — копия, а не оригинал.** Оригинал принадлежит клиенту.
Здесь она лежит, чтобы плагин собирался автономно. Совпадать должны:

- `ContractVersion.MAJOR` (проверяется при загрузке, несовпадение = плагин
  не грузится);
- сигнатуры `Provider`, `ProviderFactory`, `ProviderContext` (несовпадение =
  `NoSuchMethodError` в рантайме, что хуже).

Правило простое: **менять `provider-api` в этом репозитории нельзя.** Нужен новый
метод в контракте — это запрос к стороне клиента, а не правка здесь.

Копия сверена с клиентской: `diff -r` по каталогу `provider-api` пустой.
Плагин пользуется `httpGet`, `log` и `evalJs` — последним считается подпись
`X-Gnarly` для официальной ленты (см. «Откуда данные»). `getStorage`/`setStorage`
в контракте есть, но источнику данных они не нужны.

## Сборка

```bash
bash tools/build-plugin.sh keygen   # один раз: пара ключей Ed25519
bash tools/build-plugin.sh          # dist/provider-tiktok.jar + dist/sources.json
gradle :plugin-tiktok:test          # тесты разбора ответов
```

`build-plugin.sh` делает то, чего не делает `gradle jar`: прогоняет классы через
`d8`. `DexClassLoader` грузит только `classes.dex`, а Gradle кладёт в jar файлы
`.class`. Скрипт подписи лежит строкой в `SignerScript.kt`, а не ресурсом:
`DexClassLoader` ресурсы из jar не отдаёт, `getResourceAsStream` возвращает
`null`. Пересобирается он из `tools/signer/signer.js` скриптом
`python3 tools/make-signer.py`.

## Выпуск версии

```bash
git tag v1
git push --tags
```

Workflow соберёт, подпишет и приложит к релизу `provider-tiktok.jar` и
`sources.json`. Клиент забирает манифест с

```
https://github.com/MrRed-dev6/driftfeed-plugin/releases/latest/download/sources.json
```

то есть всегда видит последний релиз. `version` в манифесте — `github.run_number`.

Секрет `PLUGIN_SIGNING_KEY` — приватный ключ Ed25519 целиком, вместе со строками
`-----BEGIN/END-----`. Публичный ключ отдаётся стороне клиента: он зашит в
`TrustedKey.PUBLIC_KEY_BASE64` и меняется только релизом приложения.

## Видимость репозитория

Репозиторий должен быть **публичным**. Клиент скачивает `sources.json` и jar
обычным HTTPS-запросом без авторизации, а GitHub на ассеты приватного
репозитория отвечает `Not Found` — установка источника просто не начнётся.

Проверка одной строкой, без токена:

```
curl -s https://github.com/MrRed-dev6/driftfeed-plugin/releases/latest/download/sources.json
```

Должен прийти JSON. Пока приходит `Not Found`, дело не в плагине и не
в клиенте.

Открывать код не страшно: приватный ключ подписи лежит в Secrets и в файлах
не появляется, а целостность jar всё равно проверяется подписью — без ключа
подменить файл нельзя.

## Что нужно от клиента

1. `ProviderContext` с `httpGet`, `log` и `evalJs` — как в
   `ClientProviderContext`. `evalJs` нужен для подписи `X-Gnarly`.
   `getStorage` и `setStorage` плагин не вызывает.
2. `SourceIndexUrls.MIRRORS` → адрес `sources.json` этого репозитория.
3. `TrustedKey.PUBLIC_KEY_BASE64` → публичный ключ отсюда.
4. `DexClassLoader` с `parent = classLoader приложения` — иначе плагин
   не увидит `dev.client.provider.*` и упадёт при загрузке.
5. Cookie jar на `httpGet` — без него официальная лента пуста и работает
   только шлюз. Готовая инструкция — в `ИЗМЕНЕНИЯ_КЛИЕНТА.md` рядом с
   клиентом.

Ничего сверх этого плагину не требуется: ни `Context`, ни кэша. Cookie аккаунта
для официальной ленты подставляет клиент — плагин их не видит и не хранит.

## Откуда берутся данные

Почти всё — напрямую у TikTok; шлюз остаётся запасным путём.

| Запрос | Что внутри |
|---|---|
| `/embed/@<ник>` | профиль и 10 последних видео |
| `/embed/<id видео>` | видео целиком: поток, обложки, лайки, комментарии |
| `/embed/tag/<тег>` | 10 видео хештега — последний запасной путь поиска |
| `/api/comment/list/` | комментарии видео: текст, автор, лайки, ответы — **без подписи** |
| `/api/recommend/item_list/` | официальная лента «Для тебя» — подпись `X-Gnarly` + cookie аккаунта |
| шлюз `/api/feed/list` | запасная лента: поток, обложки, лайки, комментарии |
| шлюз `/api/feed/search` | настоящие результаты поиска TikTok (обычно закрыт Cloudflare) |
| поисковик `site:tiktok.com/video` | полнотекстовый поиск по описаниям видео |

**Официальная лента.** Подпись `X-Gnarly` плагин считает сам — в движке клиента,
через `evalJs`, сборкой `abogus` (MIT, чистый JS). Проверено на том же QuickJS
2021-03-27, что стоит в клиенте: 300 символов за ~3 мс. А вот cookie вошедшего
аккаунта взять неоткуда — их должен подставлять клиент в `httpGet`. Без них
TikTok отвечает `{"status_code": 0}`, то есть пустым списком, и лента уходит на
шлюз. Это единственная правка, которая нужна от клиента.

**Лента через шлюз.** Веб-API TikTok закрыт и проверен по шагам: без подписи —
пустое тело; с серверными cookie — пусто; с самодельным `msToken` — пусто; с
`X-Bogus` — пусто; с `X-Gnarly` на чистом JS — подпись принимается, но данные
всё равно пустые без аккаунта; `webmssdk.js` — 243 КБ JSVMP, который не
поднимается даже в node, а в QuickJS на телефоне тем более. Подробный разбор —
в `plugin-tiktok/README.md`.

Что это значит для пользователя: с аккаунтом лента настоящая и персональная,
посредник не участвует. Без аккаунта запрос ленты видит сторонний сервер.
Профили, видео, поиск и комментарии идут напрямую в TikTok всегда.

Поиск — каскад из трёх путей: настоящие результаты TikTok через шлюз (если
Cloudflare пустит), затем полнотекстовый индекс поисковика, затем хештег.

Из этого следуют честные ограничения:

- **свежего поиска нет** — индекс отдаёт популярное, что успело проиндексироваться,
  а не вчерашнее;
- **рекомендации только с аккаунтом** — до правки клиента лента это случайная
  выборка популярного по региону;
- **курсора у шлюза нет** — он отдаёт случайную порцию, поэтому там курсор
  плагина это номер страницы, а повторы отсеиваются на клиенте; у официальной
  ленты курсор настоящий;
- **ответов на комментарии нет** — приходит верхний уровень, `reply_comment_total`
  идёт счётчиком;
- **постраничности в поиске нет** — и `/embed`, и индекс отдают одну страницу.

## Чего в плагине нет

- **Своей подписи на Kotlin.** Алгоритм завязан на байтовые преобразования
  браузерного SDK, поэтому исполняется та же JS-сборка, что проверена в
  браузере. Вторая реализация на Kotlin означала бы две точки отказа.
- **Хранения cookie и аккаунта.** Плагин их не видит: подставляет клиент.
- **Кэша нет.** Каждый экран = запрос. Кэш логичнее держать в клиенте.
