# tiktok-plugin

Репозиторий плагина источника данных для клиента TikTok. Клиент живёт отдельно
и пишется не здесь: этот репозиторий выпускает `.jar`, который клиент скачивает
по `sources.json` и грузит через `DexClassLoader`.

## Что внутри

```
provider-api/   вендорная копия контракта клиента (только интерфейсы)
plugin-tiktok/  сам плагин: лента, поиск, видео, комментарии, профиль
tools/          сборка релизного файла: jar → d8 → jar с classes.dex → подпись
.github/        сборка и релиз на GitHub Actions
```

**`provider-api` — копия, а не оригинал.** Оригинал принадлежит клиенту.
Здесь она лежит, чтобы плагин собирался автономно. Совпадать должны:

- `ContractVersion.MAJOR` (проверяется при загрузке, несовпадение = плагин
  не грузится);
- сигнатуры `Provider`, `ProviderFactory`, `ProviderContext` (несовпадение =
  `NoSuchMethodError` в рантайме, что хуже).

Правило простое: **менять `provider-api` в этом репозитории нельзя.** Нужен новый
метод в контракте — это запрос к стороне клиента, а не правка здесь.

Единственное исключение — `getStorage`/`setStorage` в `ProviderContext`.
Их добавила сторона клиента, здесь лежит точная копия: `diff` по каталогу
`provider-api` с клиентским пустой. Плагин собран под `suspend`, типы
и имена совпали.

## Сборка

```bash
bash tools/build-plugin.sh keygen   # один раз: пара ключей Ed25519
bash tools/build-plugin.sh          # dist/provider-tiktok.jar + dist/sources.json
gradle :plugin-tiktok:test          # тесты разбора ответов
```

`build-plugin.sh` делает то, чего не делает `gradle jar`: прогоняет классы через
`d8`. `DexClassLoader` грузит только `classes.dex`, а Gradle кладёт в jar файлы
`.class`. Ресурсы (JS-скрипт подписи) переносятся в итоговый jar отдельно.

## Выпуск версии

```bash
git tag v1
git push --tags
```

Workflow соберёт, подпишет и приложит к релизу `provider-tiktok.jar` и
`sources.json`. Клиент забирает манифест с

```
https://github.com/MrRed-dev6/driftfeed-plugin/releases/latest/download/sources.json
```

то есть всегда видит последний релиз. `version` в манифесте — `github.run_number`.

Секрет `PLUGIN_SIGNING_KEY` — приватный ключ Ed25519 целиком, вместе со строками
`-----BEGIN/END-----`. Публичный ключ отдаётся стороне клиента: он зашит в
`TrustedKey.PUBLIC_KEY_BASE64` и меняется только релизом приложения.

## Что нужно от клиента

1. `ProviderContext` с сетью и `evalJs` — как в `ClientProviderContext`.
2. `SourceIndexUrls.MIRRORS` → адрес `sources.json` этого репозитория.
3. `TrustedKey.PUBLIC_KEY_BASE64` → публичный ключ отсюда.
4. `DexClassLoader` с `parent = classLoader приложения` — иначе плагин
   не увидит `dev.client.provider.*` и упадёт при загрузке.
5. `ProviderContext.getStorage` / `setStorage` — key-value хранилище
   (см. «Сессия» ниже). В контракте клиента уже есть; плагин на всякий
   случай переживает и клиент без них.

Ничего сверх этого плагину не требуется: ни `Context`, ни cookie jar, ни
конфигурации, ни кэша.

## Сессия и куки

`msToken` и `tt_webid_v2` плагин **генерирует сам** (`TikTokSession`), а не
принимает от сервера. Причина техническая: `ProviderContext` отдаёт только
тело ответа, поэтому `Set-Cookie` плагину не виден в принципе — принять куку
неоткуда.

Но принимать её и не нужно. `msToken` — клиентское значение: веб-клиент
TikTok генерирует 128 символов из алфавита base64url и отправляет их
одновременно параметром URL и заголовком `Cookie`. Плагин делает то же самое.

Сгенерированное значение сохраняется через `ProviderContext.setStorage`
и поднимается при следующем запуске, так что приложение представляется
TikTok тем же клиентом, а не новым анонимным. При чтении значение
проверяется: файл мог остаться от прерванной записи, мусор отбрасывается
и заменяется новым.

**Если методов нет** — плагин ловит `NoSuchMethodError` и живёт с сессией
в памяти. Одна строка в логе, лента работает, просто каждый старт выглядит
как новый клиент. Так новая версия плагина не ломается на старой сборке
приложения.

## Чего в плагине нет

- **`webmssdk.js`** — это код TikTok, он меняется. Кладётся в
  `plugin-tiktok/src/main/resources/tiktok/`, см. `plugin-tiktok/SIGN_SDK.md`.
  Без него `capabilities` пустые, и клиент покажет источник как «ничего не умеет».
- **Кэша нет.** Каждый экран = запрос. Кэш логичнее держать в клиенте.
